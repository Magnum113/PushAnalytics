# Push Analytics

## Назначение

Дашборд аналитики push-рассылок 05.ru должен показывать отправки, доставки, клики и заказы, атрибуцированные push-рассылкам. В дашборде можно независимо переключать проект пуша, целевое действие Mindbox и фактический проект, где был оформлен заказ.

## Текущий локальный прототип

Рабочий интерфейс находится в `PushAnalytics/dashboard/`. На 2026-07-24 он:

- загружает подтвержденные Delta-данными push-кампании с 1 мая 2026 года по 23 июля 2026 года;
- объединяет одноименные рассылки Android и iOS в одну кампанию;
- показывает точные заголовки, тексты и приложения отправки, проверенные по списку Android- и iOS-рассылок в Mindbox;
- показывает отправки, расчетные доставки, клики, CTR, целевые заказы, конверсию клик → заказ и выручку;
- фильтрует пуши по трем проектам: отдельное приложение Blizko, основной проект 05.ru и Blizko внутри приложения 05.ru;
- фильтрует кампании по месяцам: май, июнь, июль, последние 7 дней или весь период;
- позволяет переключаться между четырьмя целями и отдельно фильтровать покупки по проекту оформления;
- позволяет переключать главный график между заказами, CTR и выручкой;
- показывает лучший пуш по конверсии только при наличии атрибуцированных заказов; при нуле заказов выводит нейтральное объяснение и отдельно показывает лучший CTR как сигнал вовлечения;
- открывает по выбранному пушу обезличенный список покупок: дату, сумму, задержку после клика и состав заказа с названием товара, количеством и ценой;
- адаптирует таблицу кампаний в полноценные аналитические карточки на мобильном экране;
- открывает отдельный отчет `/blizko-july` по июльским пушам приложения Blizko: полная таблица, сравнение коммерческих текстов, выводы и ограничения;
- использует Supabase как источник сайта; локальный JSON остается промежуточным PII-free payload синхронизации.

Запуск:

```bash
cd PushAnalytics
.venv/bin/python scripts/build_dashboard_data.py --since 2026-05-01
.venv/bin/python scripts/sync_supabase_pg_meta.py
.venv/bin/python scripts/validate_supabase_data.py
cd dashboard
npm run dev
```

Локальный адрес: `http://localhost:3000/`. Июльский отчет Blizko:
`http://localhost:3000/blizko-july`.

Воспроизводимая проверка расчетов отчета находится в
`PushAnalytics/analysis/blizko_july_report.ipynb`.

Сырые Parquet-файлы кэшируются в `PushAnalytics/data/raw/`, а PII-free payload синхронизации создается в `PushAnalytics/dashboard/public/data/dashboard.json`. Оба пути исключены из Git. Браузер этот JSON не читает: `/api/dashboard` и `/api/purchases` получают данные из Supabase.

Параметр `--since` задает начало периода включительно. Необязательный `--campaigns` ограничивает количество последних кампаний на каждый проект.

## Проекты push-рассылок

Проект пуша, цель Mindbox и проект заказа — три независимых измерения:

- `blizko-app` — отдельное приложение доставки продуктов Blizko;
- `05-main` — основное приложение 05.ru и интернет-магазин техники;
- `blizko-in-05` — сценарий Blizko внутри основного приложения 05.ru;
- цель Mindbox выбирается отдельно: один пуш можно проверить по любой из четырех целей;
- проект заказа определяется по `firstPointOfContactInternalId` самого заказа и не зависит от приложения, куда был отправлен пуш.

В Delta Sharing для MobilePush нет отдельного поля с проектом или приложением-отправителем. Поэтому приложение отправки проверено по карточкам рассылок Mindbox, а классификация выполняется локально:

1. Точное переопределение `mailingId` имеет наивысший приоритет.
2. Затем применяется правило по `folderInternalId`.
3. Не классифицированные папки не попадают в набор, чтобы не показывать неверный проект.

Правила находятся в `PushAnalytics/data/project_rules.json`. Точные тексты и приложения 78 Android/iOS-вариантов хранятся в `PushAnalytics/data/push_content.json`. Папки Mindbox могут содержать кампании для разных приложений, поэтому общее правило по папке отключено: каждый `mailingId` назначен вручную после проверки фактического приложения в Mindbox.

В текущем подтвержденном наборе 78 вариантов объединены в 39 кампаний:

- май — 9 кампаний и 18 вариантов;
- июнь — 12 кампаний и 24 варианта;
- июль — 18 кампаний и 36 вариантов.

## Supabase

Идемпотентные миграции находятся в:

- `PushAnalytics/supabase/migrations/20260723_create_push_analytics.sql`;
- `PushAnalytics/supabase/migrations/20260723_add_push_purchase_details.sql`;
- `PushAnalytics/supabase/migrations/20260723_add_push_product_catalog.sql`;
- `PushAnalytics/supabase/migrations/20260723_add_push_campaign_applications.sql`;
- `PushAnalytics/supabase/migrations/20260723_classify_july_push_applications.sql`;
- `PushAnalytics/supabase/migrations/20260724_add_unique_buyers.sql`;
- `PushAnalytics/supabase/migrations/20260724_add_order_project_dimension.sql`.

Миграции применены к self-hosted Supabase `https://supabasekm.05.ru`. После синхронизации 2026-07-24 в базе находятся 3 проекта, 4 цели, 39 кампаний, 156 наборов метрик «пуш × цель», 832 записи атрибуции по переключаемым целям, 3 993 товарные строки и 1 103 сопоставленных товара каталога. По общей цели `Заказы` атрибуцировано 684 заказа.

Она создает:

- `push_projects` — справочник трех проектов;
- `push_goals` — справочник четырех целей Mindbox;
- `push_project_rules` — правила назначения проекта по папке или конкретной рассылке;
- `push_campaigns` — PII-free метаданные кампании, точный текст и список приложений, а также агрегаты отправки, доставки, клика и платформ;
- `push_campaign_goal_metrics` — заказы, выручка и задержка конверсии по каждой паре «пуш × цель»;
- `push_order_project_points` — проверяемое соответствие точки контакта Mindbox проекту оформления заказа;
- `push_attributed_orders` — обезличенные покупки с датой, суммой, кликом, задержкой и отдельным `order_project_id`;
- `push_campaign_goal_order_project_metrics` — представление метрик по тройке «пуш × цель × проект заказа»;
- `push_attributed_order_items` — товарные строки покупки, количество и цены;
- `push_products` — справочник названий, артикулов и внешних идентификаторов товаров из отдельного экспорта каталога Mindbox;
- `push_sync_runs` — журнал синхронизаций.

На клиентское чтение открыты справочники, кампании, агрегаты целей и обезличенные детали покупок. RLS включен; `anon` и `authenticated` не получают прав на запись. Идентификаторы клиентов Mindbox не сохраняются, а исходный номер заказа заменяется SHA-256-хэшем.

Для автоматической записи агрегата используется:

```bash
cd PushAnalytics
.venv/bin/python scripts/build_dashboard_data.py --since 2026-05-01
.venv/bin/python scripts/sync_supabase.py
```

Серверной синхронизации нужен `SUPABASE_SERVICE_ROLE_KEY` в локальном `.env`. Его нельзя называть `NEXT_PUBLIC_*`, передавать в браузер или коммитить. `NEXT_PUBLIC_SUPABASE_ANON_KEY` предназначен только для чтения агрегатов. До добавления серверного ключа payload можно проверить безопасно: `scripts/sync_supabase.py --dry-run`.

Для ручной синхронизации с текущим self-hosted окружением также доступен административный transport через Supabase Studio `pg-meta`:

```bash
cd PushAnalytics
.venv/bin/python scripts/build_dashboard_data.py --since 2026-05-01
.venv/bin/python scripts/sync_supabase_pg_meta.py
.venv/bin/python scripts/validate_supabase_data.py
```

Он использует только локальные переменные `VITE_SUPABASE_URL`, `SUPABASE_STUDIO_USER` и `SUPABASE_STUDIO_PASSWORD`. Большой payload автоматически делится на транзакционные порции меньше лимита Studio API; устаревшие кампании удаляются только после успешной загрузки всех порций. Скрипт предназначен для локального запуска администратором: Studio-пароль нельзя передавать в браузер, CI без защищенных secrets или клиентский код. Для регулярной серверной синхронизации предпочтителен `scripts/sync_supabase.py` с отдельным service-role ключом.

### Названия товаров в составе заказов

`ProcessingOrders.Purchases` передает позиции заказа, внутренний ID товара, количество и цены, но не название. Название хранится в каталоге продуктов Mindbox и загружается отдельно:

1. В Mindbox открыть `Данные → Продукты`.
2. Выбрать все нужные продукты или весь найденный список.
3. Нажать `Экспорт → Продуктов` и скачать CSV.
4. Положить файл, например, в `PushAnalytics/data/catalog/products.csv`. Папка исключена из Git.
5. Выполнить:

```bash
cd PushAnalytics
.venv/bin/python scripts/import_mindbox_products.py data/catalog/products.csv
```

Экспорт 283 190 продуктов выполнен 2026-07-24 и сохранен локально в `data/catalog/products.csv` (файл исключен из Git). В проектном формате нет отдельного внутреннего ID Mindbox, поэтому импортер сопоставляет `ProductIdsDarkstore`, `ProductIdsMarketplejs` и `ProductIdsWebsite` с идентификаторами реальных товарных строк. В Supabase загружены 1 103 нужных товара: названия получили 3 912 из 3 993 строк заказов, 81 строка осталась без совпадения в каталоге.

По умолчанию импортер загружает только товары, встречающиеся в заказах дашборда, записывает их в `push_products` и обновляет подписи уже загруженных товарных строк. Если названия колонок проектные, их можно указать явно:

```bash
.venv/bin/python scripts/import_mindbox_products.py data/catalog/products.csv \
  --product-internal-id-column "InternalId" \
  --name-column "Название"
```

API деталей покупки ищет товар сначала по `productInternalId`, затем по внешнему ID. Если каталог еще не загружен или конкретного товара в нем нет, интерфейс честно показывает внутренний ID/SKU и пометку об отсутствующем названии.

### Дизайн и сценарий анализа

Интерфейс упрощен 2026-07-24: сначала показывает фильтры и четыре ключевые метрики, затем динамику и лучший результат, после этого — список рассылок и компактный разбор выбранного пуша.

Примененные решения:

- убраны декоративная боковая навигация, технические ID, служебные подписи и повторяющиеся пояснения;
- вся типографика рабочих данных увеличена, мелкие моноширинные подписи исключены;
- график ограничен последними 12 рассылками, чтобы названия и значения оставались читаемыми;
- переключатель цели оставлен в одном месте вместо дублирующего бокового блока;
- таблица показывает только нужные для решения показатели: сообщение, отправки, открытия, CTR, заказы, конверсию и выручку;
- разбор пуша оставляет текст сообщения, проект, приложение, скорость заказа и платформы;
- в покупках скрыты технические хэши заказов, внутренние ID, SKU и артикулы;
- сохранены доступные состояния фокуса, зоны нажатия от 40 пикселей и отдельная мобильная компоновка.

Ориентиры: [Carbon — Dashboards](https://carbondesignsystem.com/data-visualization/dashboards/), [Microsoft — Tips for designing a great Power BI dashboard](https://learn.microsoft.com/en-us/power-bi/create-reports/service-dashboards-design-tips), [Google Design — Expressive Design research](https://design.google/library/expressive-material-design-google-research), [Figma — Web design trends 2026](https://www.figma.com/resource-library/web-design-trends/).

### Кастомная атрибуция

Текущая модель:

1. Берется событие `Clicked` по push-сообщению.
2. Объединенные профили клиентов нормализуются через `CDP.MergedCustomers`.
3. Для заказа выбирается последний клик по любой push-рассылке до первого действия заказа.
4. Заказ атрибуцируется, если между кликом и первым действием прошло не более 24 часов.
5. В результат Blizko попадает заказ, если последний клик относится к одной из выбранных Blizko-рассылок.
6. Один заказ может попасть в несколько переключаемых целей, если соответствует их условиям, но внутри одной цели засчитывается один раз.

По умолчанию интерфейс открывает общую цель `Заказы`, чтобы на тестовой выборке были видны конверсии. Узкие цели считаются строго по их текущим статусам и точкам контакта.

Важно: `push_campaigns.project_id` — проект, куда отправили push, а
`push_attributed_orders.order_project_id` — проект, где клиент фактически
оформил заказ. Например, для push «К матчу готовы? ⚽» все 14 заказов по общей
цели оформлены в отдельном приложении Blizko, хотя это не меняет правила
официальной цели Mindbox «Заказы Blizko (отдельное приложение)».

### Особенности данных push

- В `CustomerMessagesStatuses` для MobilePush нет отдельного статуса `Delivered`. Доставка рассчитывается как уникальные `Sent` минус уникальные `NotDelivered`.
- Событие открытия мобильного push представлено кликом, поэтому в интерфейсе используется прозрачная подпись `Открыли · клик`.
- Таблица `Mailings.Mailings` содержит название рассылки, но не тело push. Точные заголовки, тексты и приложения текущего периода вручную сверены в Mindbox и зафиксированы по `mailingId` в `data/push_content.json`.
- В доступной аналитической PDP-выгрузке есть только внешние идентификаторы продуктов, но нет названий. Названия подтягиваются из отдельного экспорта каталога Mindbox через `scripts/import_mindbox_products.py`; до его загрузки показывается внутренний ID/SKU. Количество и суммы строк берутся из `ProcessingOrders.Purchases`.
- Для автоматического получения полного текста в production-процессе нужно сохранять title/body в собственную БД в момент создания/отправки push либо добавить отдельный поддерживаемый Mindbox-экспорт контента. Текущей интеграции `Данные для аналитики` для тела сообщения недостаточно.
- Цель `Заказы Blizko (отдельное приложение)` сейчас возвращает 0: все доступные в Delta заказы из точек `blizkoandroid` и `blizkoios` имеют только категорию позиции `CheckedOut` / внешний статус `Create`, тогда как сама цель требует `Paid` или `Delivered`. Это не заменяется более широкой логикой, чтобы дашборд не завышал официальную цель.
- Две рассылки от 23 июля завершены в интерфейсе Mindbox, но еще не появились в Delta-статусах. До появления источниковых `Sent` они не выводятся в отчете.

## Целевые действия Mindbox

### `Заказы Blizko (отдельное приложение)`

Заказы доставки продуктов, оформленные в отдельном приложении Blizko.

Условия Mindbox:

- статус позиции заказа:
  - категория `Доставлена` — все статусы категории;
  - категория `Оплачена` — все статусы категории;
- точки контакта первого действия:
  - канал `Мобильное приложение`;
  - `blizkoandroid`;
  - `blizkoios`.

### `Заказы в приложении (ИМ)`

Заказы техники, оформленные в основном приложении 05.ru.

Условия Mindbox:

- статус позиции заказа:
  - категория `Оформлена` — все статусы категории;
- точки контакта первого действия:
  - группа `Без канала`;
  - `Android приложение`;
  - `iOS приложение`.

### `Заказ в Blizko`

Заказы доставки продуктов Blizko через точки контакта Darkstore. По бизнес-описанию цель используется для заказов Blizko внутри приложения 05.ru, однако текущие настройки Mindbox дополнительно включают сайт `Darkstore`.

Условия Mindbox:

- статус позиции заказа:
  - категория `Оформлена`;
  - конкретный статус `Создан`;
- точки контакта первого действия:
  - канал `Мобильное приложение`:
    - `AndroidAppDarkstore`;
    - `IosAppDarkstore`;
  - канал `Сайты`:
    - `Darkstore`.

### `Заказы`

Все заказы без ограничения на продукт, приложение или точку контакта.

Условия Mindbox:

- статус позиции заказа:
  - категория `Оформлена` — все статусы категории;
  - категория `Оплачена` — все статусы категории;
  - категория `Доставлена` — все статусы категории;
- точки контакта первого действия:
  - все каналы;
  - все точки контакта.

### Требование к дашборду

- Целевое действие должно быть отдельным измерением данных.
- Проект push-рассылки должен быть независимым измерением и не выводиться автоматически из выбранной цели.
- Пользователь должен иметь возможность переключать цель или фильтровать отчет по одной из четырех целей.
- Цель `Заказы` является общей, поэтому ее показатели могут включать заказы из более узких целей. Значения целей нельзя автоматически суммировать без проверки их пересечений.
- Узкие цели различаются не только продуктом, но и статусами и точками контакта первого действия.
- Для сверки с официальным отчетом Mindbox нужно дополнительно получить `goalId` каждой цели.

Доступ к метаданным интеграции проверен 2026-07-23. Доступны необходимые таблицы:
